# 生成评估标准口径（SOP）

> 最后更新：**2026-09-29（对接流程整理 + 加氢口径确立）**
> 定位：**所有生成评估必须遵守的唯一口径**
> 起因：同一模型的不同批次分子，对接打分可差 2+ kcal/mol——
> 已证实差异来自**采样制度 / 子集过滤 / 尺寸分布 / 对接准备 / 配体坐标系**五项口径不一致，而非模型变化。

---

## 零、为什么必须有这套 SOP

同一批 674 个分子（Original 1000-attempt），只改变统计口径：

| 口径 | n | 对接中位 |
|---|---:|---:|
| 全量有效分子 | 674 | −9.51 |
| 只取 R1–R5 合规 | 344 | **−8.98** |
| 只取 R1–R5 违规 | 330 | **−10.10** |

**同批分子差 1.12 kcal/mol**。再叠加采样制度差异（resamplings 0 vs 10），
跨数据集的 2.2 kcal/mol 差距完全可以只由口径造成。因此：

> **任何跨批次 / 跨 checkpoint / 跨模型的对接比较，必须先在生成、后处理、对接、统计四个阶段对齐口径。**

2026-09-30 的加氢对照实验又追加三条硬结论（证据见 §八）：

1. 旧条目「加 H 会导致分数爆炸（52% 异常值）」**在全仓库找不到任何支撑产物**，且被实测否证；
   真正的坑是 `Chem.AddHs()` **漏传 `addCoords=True`**（见 §二.3）；
2. **同协议重跑本身就有 p95 ≈ 0.37 kcal/mol 的抖动** → 任何 < 0.4 的差异不得当作效应；
3. 采集线与生成评估线的**配体坐标系不一致**（见 §三.0）→ 对接起点不同。

## 一、生成阶段（固定项）

| 项 | 规定 | 备注 |
|---|---|---|
| attempts | **固定数，不补无效分子** | 项目硬规则 |
| seed | `seed = gpu_id`（1-based），必须记录 | 同上 |
| resamplings | **统一为 10**（主线脚本默认）；若需 resamplings=0 对照，必须显式声明 | 200k 采集为 0，不可与主线混比 |
| timesteps | **统一 t500** | 200k 采集为 t1000 |
| 尺寸采样 | **条件先验**（不得用 `randint(10,30)`） | 200k 用 randint，HA 偏小 ~3 |
| reconstruction | `openbabel` | 统一 |
| 产出 | `molecules.sdf` + 生成配置快照 | 必须留档 |

## 二、后处理阶段（固定顺序）

1. 逐记录 `Chem.SanitizeMol`（宽松 sanitize 判定，失败计入 `sanitize_rate` 分母）；
2. **取最大片段（largest fragment）** —— 统一做，消除碎片污染；
3. **加氢：固定做**，且 **必须 `Chem.AddHs(mol, addCoords=True)`**。
   - 依据：AutoDock Vina 官方 manual —— "polar hydrogens are needed in the input structures
     to correctly type heavy atoms as hydrogen bond donors"（https://vina.scripps.edu/manual/）；
     UniDock 的 SDF 分型表（`unidock_tools/modules/ligand_prep/torsion_tree.py`）靠
     `[#1][#7,#8,#9,#15,#16] → HD` 匹配供体氢，无显式 H 就没有任何 `HD` 原子。
   - **`addCoords` 不可省**：漏传时 100/100 分子的氢被放在原点，UniDock 产出全部作废（§八 D 臂）；
     即使不报错，也会把分数打爆——**这才是旧「52% 爆炸」说法的真正来源**。
   - 非极性氢不必刻意删除：Vina 是 united-atom 打分，非极性氢由分型表标为 `H`(invisible)。
4. **不加电荷** —— 固定关闭 Gasteiger。
   - 依据：Vina official manual —— "**AutoDock Vina ignores the user-supplied partial charges.**"
     以及 "Calculating grid maps and assigning atom charges is not needed."
   - 仅当改用 `--scoring ad4` 时才必须赋电荷（AD4 打分有静电项），届时另立口径。
   - 注意：`unidock_tools` 的配体准备会**自己**算 Gasteiger，外部再算一遍是纯冗余。
5. 过滤 `canonical_smiles` 非空；
6. 记录四个计数：`n_attempts` / `n_sanitize` / `n_lf` / `n_h`。

## 三、对接阶段（唯一固定流程）

### 3.0 前置约定：配体坐标系（必须先声明属哪一类）

2026-09-30 核实的实测事实：

| 来源 | 首原子坐标 | 坐标系 |
|---|---|---|
| 原始采集 SDF `runs/diffsbdd_collect/**/molecules/rank_00/shard_0000/*.sdf` | (1.56, −1.65, −1.44) | **质心归零**（绝对位置已丢） |
| 200k 端点池 `analysis/reference_support_experiment/docking_subset/sdf/part_0000.sdf` | (4.86, −2.32, −1.08) | 质心归零 |
| 生成评估 `analysis/..._generation_1000_260902/molecules.sdf` | (210.0, 213.1, 173.7) | **受体坐标系**（盒心 207/212/173） |
| UniDock 输出 pose | (203.2, 210.9, 176.1) | 受体坐标系 |

根因：

- **采集线**全程 zero-centered（`ddpo/integration/diffsbdd_model.py`：`sample_normal_zero_com` /
  `remove_mean_batch` / "Coordinates are kept zero-centered"），且
  `ddpo/utils/molecule_semantics.py` **没有任何平移补偿** → 写出的 SDF 质心在原点；
- **生成评估线**由 `DiffSBDD/generate_ligands.py` → `lightning_modules.py:975`
  （"Pocket's center of mass"）**平移回 pocket 质心** → 坐标在受体坐标系。

后果：

> 200k 端点对接是**盲对接**（配体从原点被 UniDock 搬进 20 Å 盒）；
> 生成评估对接的起点已在盒内。**两条线的对接分数不可直接比较。**
> 影响量尚未量化（实验见 §九）。

### 3.1 唯一命令行

```bash
unidock --receptor data/8gjl.pdbqt \
  --gpu_batch <LF + AddHs(addCoords=True) 后的 SDF 列表> \
  --center_x 207.293 --center_y 212.430 --center_z 172.771 \
  --size_x 20 --size_y 20 --size_z 20 \
  --scoring vina --search_mode fast --num_modes 1 --seed 42 \
  --verbosity 1 --cpu 0 --max_gpu_memory 0 --dir <out>
```

| 参数 | 值 | 说明 |
|---|---|---|
| 二进制 | `/opt/unidock-1.1.3/bin/unidock` | 版本必须进协议指纹 |
| receptor | `data/8gjl.pdbqt` | sha256 必须进协议指纹 |
| box | center 207.293 / 212.430 / 172.771，size 20³ | 与五模型横评、ChEMBL 参照对接一致 |
| scoring | `vina` | UniDock 默认也是 vina，但**必须显式传** |
| search_mode | `fast` | **会覆盖 `--exhaustiveness`**，两者不要同时写 |
| num_modes | 1 | UniDock 默认是 9，必须显式写 |
| seed | 42 | **UniDock 默认是 0，必须显式写**（决定随机搜索可复现） |
| verbosity / cpu / max_gpu_memory | 1 / 0 / 0 | 必须显式传，避免走默认值 |
| timeout | 3600 s | 训练 reward 路径旧值为 600 s，已统一 |

- `grep -rn "SCORE_PATTERNS" ddpo scripts` → 空；
- `GetMolFrags` 只出现在 `ligand_prep.py`（LF 真实现）；

### 3.3 分数解析（**结构化取值，不做值域砍**）

2026-09-30 核实：**UniDock 不写 `REMARK VINA RESULT:`**（实测输出文件里 `'REMARK' in text` 为 False）。
唯一实际的载体是属性块：

```
> <Uni-Dock RESULT>
ENERGY=   -6.897  LOWER_BOUND=    0.000  UPPER_BOUND=    0.000
INTER + INTRA:          -6.897
INTER:                  -6.897
INTRA:                   0.000
UNBOUND:                 0.000
```

因此解析规则是：

1. **锚定 `> <Uni-Dock RESULT>` 块**取 `ENERGY`，**禁止**全文搜 `ENERGY=`；
   实测旧实现（`SCORE_PATTERNS` 里最松的那条 `ENERGY=`）是 1300/1300 个文件的**唯一**命中路径
   —— 一个 `ENERGY=` 就能污染整批。
2. 同时读出 `INTER + INTRA` / `INTER` / `INTRA` / `UNBOUND` 做**自洽校验**：
   `ENERGY == INTER+INTRA == INTER` 且 `INTRA == 0`。不自洽 → `parse_error`。
   ⚠️ 注意：UniDock 的**失败输出同样自洽**（只是值为非物理巨大正数），所以自洽校验
   **抓不到**这类失败，必须靠下一节的状态标记。
3. **不设 `−30 ≤ s ≤ 0` 这类闸门**（原写法错误，见 §八.6）。分数一律保留，只打状态标记。

### 3.3.1 分数状态（三态，替换原「≥0 即无效」）

| 状态 | 判据 | 处理 |
|---|---|---|
| `ok` | `s ≤ 0` | 计入主指标（对接中位） |
| `positive_no_binding` | `0 < s`（实测真实值在 **+2.85 ~ +44.9**，200k 全量到 +331） | **保留**，单独报 n 与占比；这是"不结合"的真实结果，删掉会造成幸存者偏差 |
| `suspect_backend` | `s > 100`（生成批实测有一处空档：真实最大 +44.9 → 失败最小 +2051） | 单列、单计数；**不进 mean**，也不静默丢弃 |

**为什么要三态而不是二态**：实测显示**不存在能干净区分"真实弱结合"与"UniDock 失败输出"的阈值**——
- 生成批有明显空档（44.9 vs 2051，40 倍）→ 可用 100；
- 但 200k 全量正分**连续分布到 +331**（≤50 有 89 条、(50,100] 13 条、(100,1000] 8 条），无空档。
所以任何"砍值域"的做法都会在某一批上误删真实结果。**正确做法是把不确定性显式标出来，而不是砍掉。**

下界：两批实测极值分别为 **−13.0**（生成批）与 **−11.5**（200k 池），从未接近 −30，
故不设下界；若未来出现 `< −25`，按 `suspect_backend` 记录并人工复核。

**禁用 `score_mean` 做任何对比**（mean 对单条垃圾分毫无抵抗力；median 天然稳健）。

### 3.4 失败与重试

- 整批 rc=−11 时按 **500 子批降级重试**（坏分子只污染自己的子批）；
- 分数按 §3.3.1 打三态标记，**不删数**；
- 主指标（对接中位）只用 `ok` 子集，但**必须同时报** `positive_no_binding` 与
  `suspect_backend` 的条数与占比——否则无法解释分母变化。

### 3.5 协议指纹（新增，必须实现）

把以下字段 hash 成 `docking_protocol_id`，写进每个 run 的 manifest 与每张结果 CSV：

```
unidock 版本 + receptor sha256 + box(center/size) + scoring + search_mode
+ num_modes + seed + ligand_prep(fragment_policy, add_hydrogens, add_coords, charges)
+ 配体坐标系类别（centered_zero | receptor_frame）
```

> 两次对接只要 `docking_protocol_id` 不同，**不许进同一张对比表**。

## 五、跨数据集比较规则

1. **一律 size-matched**：按 HA（重原子数）分层重采样匹配后再比（`corr(HA, docking) = −0.64`，尺寸是强混淆）；
2. **同子集定义**：要么全量、要么 clean&HA10–30，不许一边全量一边合规；
3. **同采样制度**：resamplings / timesteps 必须一致，否则在结论中显式声明不可比；
4. **同配体坐标系**：centered_zero 与 receptor_frame 不可混比（§三.0）；
5. **同 `docking_protocol_id`**；
6. **差异判定**：bootstrap 95% CI 不重叠才称"有差异"；否则写"在噪声范围内"。
   参考量级：**同协议重跑 p95 = 0.37 kcal/mol**，故 <0.4 的差异默认视为噪声。

## 八、2026-09-30 口径变更依据（实测汇总）

### 8.1 加氢对照（生成批：260902 `molecules.sdf`，1000 attempts）

| 口径 | n | 对接中位 |
|---|---:|---:|
| A 不加 H（现状） | 1000（异常 43 条） | −7.964 |
| B 加 H（`addCoords=True`） | 974（异常 18 条） | −8.093 |
| **配对比较（剔异常后）** | **935** | **Δ中位 = −0.012** |

- p95\|Δ\| = 0.947；\|Δ\|>0.5 占 8.9%；>1.0 占 4.7%；Spearman 0.9705；**top-50 换 3 个**。
- 我的 A 臂复现了历史中位（−7.964 vs 历史 −7.937）→ harness 可信。

### 8.2 加氢对照（200k 端点池，300 分子）

| 项 | 值 |
|---|---|
| Δ中位（B−A） | **−0.011** |
| p95\|Δ\| | 0.575 |
| top-50 重合 | 47/50 |

### 8.3 噪声与混淆项基线

| 对照 | Δ中位 | p95\|Δ\| | Spearman |
|---|---:|---:|---:|
| 同协议重跑（harness A vs 历史 A） | +0.004 | 0.371 | 0.989 |
| seed 0 vs seed 42 | 0.000 | 0.184 | 0.986 |

### 8.4 `addCoords` 缺失的后果（D 臂）

`Chem.AddHs(mol)`（漏传 `addCoords=True`）→ **100/100 分子的氢被放在原点**，
几何退化，UniDock 产出不可用。**这是旧「52% 异常值」论断的合理根因。**

### 8.5 结论

1. **加氢不解释「DiffSBDD 打分偏低」**：中位差 0.012，而 DiffSBDD 与对标模型差 0.55–1.9 kcal/mol
   （外部基准 ShallowBench 2026 在控制集上测得 DiffSBDD −5.40 vs TargetDiff −7.33）。
   论文中「DiffSBDD 对接偏低」应归因到**尺寸/极性分布 + 模型固有结合倾向**，**不得**写成氢处理问题。
2. 加氢只影响**排序边角**（top-50 换 3 个）→ **分布类统计可复用历史值，排名/top-k 必须重跑**。
3. 但**协议仍统一到「加 H」**，因为它是 Vina 官方硬要求，且决定供体分型是否正确。

### 8.6 分数解析与"越界值"的真实构成（推翻旧闸门写法）

**（a）UniDock 不写 `REMARK VINA RESULT:`。** 实测 1300/1300 个输出文件的匹配全部落在
最松的正则 `ENERGY=` 上 → 单条 `ENERGY=` 即可污染整批。

**（b）"越界"不是解析错误，而是 UniDock 的失败输出。** 失败样例的真实文本：

```
> <Uni-Dock RESULT>
ENERGY=110590696.000  LOWER_BOUND=    0.000  UPPER_BOUND=    0.000
INTER + INTRA:    110590696.000
INTER:            110590696.000
INTRA:                   0.000
```

`ENERGY` 就是 affinity 本身（正常文件 `−6.897`，与 `INTER` 一致）；失败时被写成非物理巨大正数，
**块内自洽、rc=0、pose 照常写出** —— 所以只能靠量级识别。

**（c）正分构成（决定闸门能不能用值域实现）**：

| 数据集 | 正分条数 | ≤50 | (50,100] | (100,1000] | >1000 |
|---|---:|---:|---:|---:|---:|
| 生成批（1000 attempts） | 42 | ~28（真实最大 **+44.9**） | — | — | **7**（2051 ~ 1.1×10⁸） |
| 200k 全量（135,107） | 110 (0.08%) | **89** | 13 | 8 | 0（最大 +331） |

- 生成批：真实正分最大值 +44.9，失败最小值 +2051 → **有 40 倍空档**，阈值 100 可用；
- 200k 全量：正分**连续分布到 +331，无空档** → 无法用阈值干净切分。

**结论：`−30 ≤ score ≤ 0` 这条闸门是错的。**
- `s ≤ 0` 会**误删真实的不结合结果**（200k 批的 89 条 ≤50 正分，最小 +2.96）→ 幸存者偏差；
- `−30` 下界在本项目数据里**从未触及**（实测 min 为 −13.0 / −11.5），是无依据常量；
- 根本原因：**数据里不存在能区分"真实弱结合"与"后端失败"的统一阈值**。
  ⇒ 改为 §3.3.1 的**三态标记 + 不删数**。
