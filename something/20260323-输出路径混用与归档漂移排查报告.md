用户反馈现象：
- 训练主日志位于 `OUT/diffsbdd-ddpo-qed-sa-test_20260323_193553/`（及同批次 run 目录）
- 但分子记录文件落在仓库根目录 `molecules/`

目标：
- 检查 `output_dir`、`trainer.default_root_dir`、记录器输出路径是否对齐
- 汇总所有“输出路径混用/归档漂移”混乱点
- **不修改现有代码**（本报告仅分析）

## 三、关键现场事实（证据汇总）

### 3.1 run 目录存在，但内容不完整且分裂

以用户指出的 run 为例：
- `OUT/diffsbdd-ddpo-qed-sa-test_20260323_193553/` 仅有：
  - `config.yaml`
  - `lightning_logs/version_0/{events,hparams}`
  - 缺失 `molecules/`、`checkpoints/`、`epochs/`、`logs/batch_stats` 等

同日其它 run 也出现“部分文件存在、部分缺失”的分裂状态：
- `174921`：只有 `config.yaml`（有 `training_*.log`）
- `175016`：只有 `config.yaml`（有 `training_*.log`）
- `175009`：有 `config.yaml + lightning_logs`（有 `training_*.log`）
- `193600`：只有 `config.yaml`（有 `training_*.log`）

说明：同一训练链路在多个时间戳目录下留下“半成品 run 目录”，归档一致性不足。

### 3.2 分子记录统一落到了仓库根 `molecules/`

实际存在：
- `/home/md666/data/disk6/DiffB110/molecules/molecules.csv`
- `/home/md666/data/disk6/DiffB110/molecules/epoch_statistics.csv`

并且时间戳与 19:36~19:37 训练窗口一致：
- `molecules.csv` 修改时间：`2026-03-23 19:36:05`
- `epoch_statistics.csv` 修改时间：`2026-03-23 19:37:28`

这与 run 目录（`193553`/`193600`）时间窗对齐，说明这些记录并非历史遗留，而是本次链路写入。

### 3.3 根目录 molecules 文件被覆盖风险已发生

`molecule_recorder.py` 采用写入模式 `'w'` 初始化：
- 每次新建记录器都会重写 `molecules.csv` 与 `epoch_statistics.csv`
- 导致跨 run 归档被覆盖（典型归档漂移）

现场文件内容也印证“非 run 隔离”特征：
- `molecules.csv` 当前仅表头
- `epoch_statistics.csv` 仅有少量 epoch 行（1~3）
- 无法按 run 回溯

### 3.4 配置中声明的输出字段未被完整消费

`configs/ddp_gpu_qed_sa_test.yaml` 中：
- `output.dir: ./OUT/<run_name>_<YYYYMMDD>_<seq>`
- `output.metrics_file: metrics.csv`
- `output.molecules_dir: molecules`

但当前链路里：
- `output.dir` 被入口脚本解析并用于 `training_*.log`、`config.yaml`、TensorBoard
- `output.metrics_file` 未见产出
- `output.molecules_dir` 未参与记录器实际落盘路径决策

结果：配置“看起来可控”，但关键记录路径实际上受其它变量驱动。

## 四、路径链路追踪（从代码到落盘）

### 4.1 `output_dir`（入口层）

`ddpo/main_diffsbdd_lightning.py` 中：
- 读取 `config["output"]["dir"]`
- 替换 `<run_name>/<YYYYMMDD>/<seq>` 得到 run 目录
- 将 `training_*.log`、`config.yaml`、`TensorBoardLogger(save_dir=output_dir)` 指向该目录

这一层是对齐 `OUT/...` 的。

### 4.2 `trainer.default_root_dir`（Lightning 内部根）

`pl.Trainer(...)` 创建时未显式传 `default_root_dir`。

随后在 `LightningDDPOModule.setup()`：
- `output_dir = self.trainer.default_root_dir or "./outputs"`
- `MoleculeRecorder(output_dir)`

现场结果显示此处 `self.trainer.default_root_dir` 实际为当前工作目录（仓库根），因此记录器写到了：
- `<repo_root>/molecules/`

即：**记录器未继承入口 `output_dir`，而是继承了 trainer 默认根**。

### 4.3 记录器实际写盘策略

`ddpo/utils/molecule_recorder.py`：
- 记录目录：`os.path.join(output_dir, "molecules")`
- 文件固定名：`molecules.csv`、`epoch_statistics.csv`
- 打开方式：`'w'`

因此一旦 `output_dir` 不是 run 目录（而是仓库根），就会导致：
1. 路径漂移到根目录
2. 不同 run 相互覆盖
3. 无法按 run 归档

## 五、混乱点清单（系统化）

| 编号 | 混乱现象 | 现场证据 | 直接原因 | 风险 |
|---|---|---|---|---|
| C1 | 训练日志在 `OUT/...`，分子记录在根 `molecules/` | `training_*.log` 在 run 目录；`molecules/*.csv` 在仓库根 | `output_dir` 与 `trainer.default_root_dir` 双根并存 | run 归档断裂，难以审计 |
| C2 | run 目录内容不完整、存在“半成品” | 多个 `20260323_*` 目录仅有 `config` 或仅部分文件 | 训练中断/提前退出 + 无统一收尾归档 | 历史 run 难以判定有效性 |
| C3 | 分子记录跨 run 覆盖 | `molecules.csv`/`epoch_statistics.csv` 固定文件名且 `'w'` 打开 | 记录文件无 run 隔离 | 旧实验证据丢失 |
| C4 | 配置项与实际落盘行为不一致 | `output.molecules_dir/metrics_file` 配置存在但未形成对应 run 内产物 | 配置字段未被关键路径消费 | 用户误判“已配置即生效” |
| C5 | 目录结构偏离文档约定 | 当前 run 下无 `epochs/`、`logs/molecules_*.csv`、`training_summary.csv` | 现实现代码路径与文档期望不一致 | 运维与排障成本高 |
| C6 | 产物所有者为 root（本次样本） | 根 `molecules/*.csv` UID/GID 为 root | 运行上下文混杂 | 后续普通用户写入/清理可能受阻 |

## 六、与项目路径文档的对照偏差

`docs/project_path.md` 与项目规则强调：
- 输出应统一进入 `OUT/<run_name>_<date>_<seq>/...`
- 运行与归档路径应避免混用

当前 qedsa 训练链路（3月23日样本）出现：
- 入口输出（log/config/TB）在 `OUT/...`
- 分子记录在仓库根 `molecules/`
- run 目录缺少多类预期文件

属于典型“输出路径混用 + 归档漂移”。

---

## 七、结论

本次问题不是单点偶发，而是路径控制面存在“双源头”：

1. 入口层使用 `output.dir -> OUT/<run...>`
2. 模块层使用 `trainer.default_root_dir` 作为记录器根

两者未强制对齐，造成：
- 同一次训练的不同产物落在不同根目录
- 分子记录跨 run 覆盖
- run 目录归档不完整

因此，用户观察到的“训练日志在 OUT，但分子记录掉到根 molecules”已被现场证据确认。

---

## 八、后续建议（仅建议，不改代码）

为后续修复准备，可按优先级考虑：

1. 明确唯一输出根（single source of truth），所有记录器和回调只接受该根派生路径
2. 禁止记录器写固定文件名到共享目录（至少 run 级隔离）
3. 将 `output.molecules_dir`、`output.metrics_file` 接入真实写盘路径，避免“配置假生效”
4. 增加 run 完整性检查（结束时核对关键文件是否齐全）
5. 统一运行用户身份，避免 root/普通用户混写

> 以上为诊断结论与改进方向；本次按要求未做任何代码修改。
