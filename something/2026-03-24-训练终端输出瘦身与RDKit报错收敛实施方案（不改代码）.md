## 2. 为什么“底层输出难禁用”

当前噪声中最难处理的是 RDKit/OpenBabel 报错：
- `Explicit valence ...`
- `Both bonds on one end of an atropisomer ...`
- `*** Open Babel Error ...`

它们大量来自 C/C++ 层直接写入 `stderr`，并非 Python `logging`，因此：
- `logging.getLogger(...).setLevel(...)` 无法完全拦截
- `warnings.filterwarnings(...)` 无法完全拦截

结论：不改代码时，最稳妥的方式是**进程级 stdout/stderr 分流重定向**。

---

## 3. 不改代码的落地方案（推荐）

## 3.1 运行方式：stdout/stderr 分流

在正常用户终端（非 root）中执行：

```bash
cd /home/md666/data/disk6/DiffB110
mkdir -p OUT/console_logs

TS=$(date +%Y%m%d_%H%M%S)

# stdout: 终端关键输出 + 持久化
# stderr: 底层警告/报错单独落盘（不进主终端）
bash scripts/run_rl_qed_sa_test.sh \
  1> >(tee "OUT/console_logs/train_stdout_${TS}.log") \
  2> "OUT/console_logs/train_stderr_${TS}.log"
```

效果：
- 终端主要保留 stdout（训练进度、epoch 汇总等）
- RDKit/OpenBabel 大量 stderr 不再刷主屏
- `stderr` 全量保留在 `train_stderr_*.log`

> 若希望终端绝对安静，可把 stdout 也重定向到文件；但不建议，会损失实时可观测性。

## 3.3 日志查看分工

建议按“信息分层”查看：

1. **主状态（人看）**
   - `OUT/console_logs/train_stdout_*.log`
   - 关注：epoch 进度、loss/reward、训练是否完成

2. **底层告警（技术排障）**
   - `OUT/console_logs/train_stderr_*.log`
   - 关注：RDKit/OpenBabel、稀有异常、堆栈错误

3. **训练主日志（程序日志）**
   - `OUT/<run_dir>/training_*.log`
   - 关注：组件初始化、输出目录、trainer 状态

## 4. 三档噪声控制策略（不改代码）

## A档（推荐，平衡）
- stdout 显示 + tee 持久化
- stderr 单独文件
- 适合日常训练

## B档（最安静）
- stdout/stderr 全部文件化
- 终端几乎无输出
- 适合超长任务后台跑

```bash
bash scripts/run_rl_qed_sa_test.sh \
  > "OUT/console_logs/train_all_${TS}.log" 2>&1
```

## C档（快速诊断）
- stdout 正常
- stderr 也显示（不分流）
- 适合短时间调试“为何失败”

---

## 5. 风险与边界

1. 分流不会减少真实报错，只是改变展示位置
2. 若程序把关键异常也写到 stderr，主终端可能看不到细节（但文件里有）
3. DDP/多进程时，stderr 文件可能很大，建议按时间戳分文件

---

## 6. 验收标准（本方案成功判据）

执行一次训练后，应满足：

1. 主终端不再被 RDKit/OpenBabel 警告刷屏
2. `OUT/console_logs/train_stderr_<ts>.log` 能看到完整底层警告
3. `OUT/console_logs/train_stdout_<ts>.log` 能看到训练关键进度
4. `OUT/<run_dir>/training_*.log` 仍正常生成
