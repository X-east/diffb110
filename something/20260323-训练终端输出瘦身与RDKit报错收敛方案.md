# 2026-03-23 训练终端输出瘦身与RDKit报错收敛方案

## 1. 目标

当前训练终端输出存在两个明显问题：

1. **无用信息过多**：大量 `[DEBUG]`、`[Rank 0]`、Ray 初始化、逐步扩散过程的杂项输出混在主终端里，影响观察真正关键训练状态。
2. **RDKit / OpenBabel 报错直接刷屏**：如
   - `[19:36:50] Explicit valence for atom # 5 N, 4, is greater than permitted`
   - `DEPRECATION WARNING: please use MorganGenerator`
   - `*** Open Babel Error in TetStereoToWedgeHash`
   这些信息直接写到终端，而不是被统一收纳进日志文件。

用户希望保留的终端核心信息应当压缩成：

1. **训练启动信息**
   - GPU 信息
   - 配置路径
   - 使用卡数
   - Batch / Max Epochs
2. **每个 epoch 的生成进度**
   - 单行覆盖显示，不要刷屏
3. **每个 epoch 结束后的汇总指标**
   - `Loss`
   - `Reward`
   - `QED`
   - `SA`
   - `Valid Ratio`
4. **checkpoint 保存信息**
5. **训练完成信息**

本文件给出一个**不改代码前提下的设计方案文档**：说明应该改哪些位置、如何改、预期效果是什么。

## 2. 现状诊断

## 2.1 当前终端噪声的主要来源

当前终端输出噪声主要来自 4 类来源。

### 来源 A：启动脚本本身输出过多环境信息
文件：`scripts/run_rl_qed_sa_test.sh`

当前会输出：
- `Project root`
- `Conda env`
- `Python`
- `Config`
- `GPUs`
- `Seed`
- `Log level`
- `Start time`
- `nvidia-smi --list-gpus`

这些本身不算严重，但可以再压缩排版，让启动区更像“banner + 核心摘要”，而不是 shell 脚本流水账。

---

### 来源 B：采样阶段的进度条与警告直接使用 `print()` 输出到 stdout
文件：`ddpo/integration/diffsbdd_model.py`

当前已经有单行覆盖进度：
- `[{Epoch}] 生成中: ...`
- `[{Epoch}] 生成完成: ...`

这部分**应该保留**，因为它正是用户希望看到的“每个 epoch 生成进度”。

但这个文件里还存在一些直接 `print()` 的 warning：
- `Warning: CoG drift ...`
- `Warning: Mean is not zero ...`

这些会打断单行进度显示，破坏终端整洁性。

---

### 来源 C：Lightning 模块中大量 `self.print()` 调试输出
文件：`ddpo/trainer/lightning_ddpo_module.py`

目前会向终端输出很多调试信息：
- `[Rank 0] Starting Ray initialization...`
- `[Rank 0] Calling ray.init ...`
- `[Rank 0] Ray initialized successfully`
- `[DEBUG] Generated 0 molecules`
- `[DEBUG] After filter: ...`
- `[DEBUG] Rewards: min/max/mean`
- `[DEBUG] QED list length ...`
- `[DEBUG] QED values ...`
- `[DEBUG] SA values ...`
- `[Epoch ...] Batch ...`

其中大多数属于**调试信息**，应该写入 log 文件，而不应进入终端主视图。

---

### 来源 D：RDKit / OpenBabel 直接写 stderr，绕过 Python logging
文件涉及：
- `ddpo/main_diffsbdd_lightning.py`
- `ddpo/utils/suppress_warnings.py`
- 以及 reward / molecule conversion / sanitize 相关代码路径

当前虽然做了：
- `logging.getLogger('rdkit').setLevel(logging.ERROR)`
- `logging.getLogger('openbabel').setLevel(logging.ERROR)`
- `warnings.filterwarnings(...)`

但**这挡不住底层 C++ 层直接往 stderr 写的告警**。

所以会出现：
- `Explicit valence ...`
- `Both bonds on one end of an atropisomer ...`
- `*** Open Babel Error in TetStereoToWedgeHash`

这些不是普通 Python `logging`，而是底层库直接刷终端。

## 5. 具体方案

## 5.1 启动脚本层：保留 banner，但精简为“启动摘要”

文件：`scripts/run_rl_qed_sa_test.sh`

### 当前问题
脚本输出的信息太散，偏 shell 调试风格，不够面向训练观察。

### 建议改法
把当前多行环境信息整理成更稳定的启动摘要块：

1. 保留：
   - 标题
   - GPU 列表
   - 使用 GPU 数量
   - Config 路径
   - Seed
   - Log level
2. 不必在终端保留：
   - Python 可执行路径
   - Conda env 细节
   - Project root
   - 其他脚本级冗余信息

### 预期效果
终端一开始就只展示“这次训练的关键信息”，不会被环境细节淹没。

---

## 5.2 训练入口层：建立“终端 logger”和“文件 logger”分级

文件：`ddpo/main_diffsbdd.py` 中的 `setup_logging()` 会被 `ddpo/main_diffsbdd_lightning.py` 复用。

### 当前问题
现在的 logger 同时把相同级别信息写到：
- 文件
- 控制台

这样一来，只要代码里 `logger.info(...)` 多，终端就会很吵。

### 建议改法
把日志体系拆成两级：

#### 方案 A：文件全量，终端精简
- 文件 handler：保留 `DEBUG` 及以上
- 终端 handler：只保留少量 `INFO`，并且只显示训练摘要类消息

#### 方案 B：增加专用 logger 名称或 filter
例如定义：
- `train_file_logger`：写全量技术日志
- `train_console_logger`：只写核心摘要

更简单的实现方式是给 console handler 加 filter，只允许以下模式通过：
- 启动 banner
- epoch summary
- checkpoint summary
- training completed

### 预期效果
即使内部仍记录了很多细节，终端也只显示少量高价值内容，完整信息仍可在 `training_*.log` 查看。

---

## 5.3 RDKit / OpenBabel 告警处理：不要直接刷终端，改为重定向到日志

文件：
- `ddpo/utils/suppress_warnings.py`
- reward / sanitize / SMILES 转换相关代码路径

### 当前问题
现在仅仅设置 Python logging level：
- 挡不住 RDKit C++ 层 stderr
- 挡不住 OpenBabel C++ 层 stderr

### 建议改法
这里分成两层。

#### 第一层：真正关闭 RDKit Python 侧日志
在 `setup_chemistry_logging()` 中，不只设置 `logging.getLogger('rdkit')`，还要显式调用 RDKit 自己的日志关闭接口。

大致方向：
- 关闭 `rdApp.warning`
- 关闭 `rdApp.error`
- 必要时关闭 `rdApp.info`

这样可压掉大部分 RDKit 的标准报错输出。

#### 第二层：对特定分子转换 / 评分代码块做 stderr 重定向
对如下“已知高噪声”操作，在局部上下文中把 stderr 导到日志文件，而不是终端：
- `Chem.MolFromSmiles(...)`
- `Chem.SanitizeMol(...)`
- OpenBabel 转换
- 计算 QED / SA 时的无效分子处理

注意这里**不建议全局吞掉 stderr**，因为那会隐藏真正致命错误。

更合理的是：
- 在 reward 计算的分子级循环中，捕获这些噪声
- 把原始 stderr 文本写入训练日志或专用 `chemistry_warnings.log`
- 终端只显示聚合后的摘要，例如：
  - `Chem warnings: 13 invalid molecules this epoch (details in log)`

### 预期效果
终端将不再被：
- `Explicit valence ...`
- `atropisomer ...`
- `TetStereoToWedgeHash`
- `MorganGenerator`
刷屏。

同时，错误细节没有丢，而是进入 log 文件，后续仍可排查。

---

## 5.4 Lightning 模块层：去掉 `self.print()` 调试洪水，只保留 epoch 级摘要

文件：`ddpo/trainer/lightning_ddpo_module.py`

### 当前问题
这个文件是终端噪声的主来源之一。当前终端里大量输出来自：
- setup() 中的 rank / ray 输出
- forward() 中的 `[DEBUG] Generated ...`
- `[DEBUG] Rewards ...`
- `[DEBUG] QED list length ...`
- `[DEBUG] SA values ...`
- training_step() 中 batch 级摘要

这些对于排查很有用，但不应该默认出现在主终端。

### 建议改法
将该文件的输出分三类。

#### 类别 1：终端保留
只保留：
1. `on_train_start()` 的训练开始摘要
2. `on_train_epoch_end()` 的 epoch 汇总
3. `on_save_checkpoint()` 或 checkpoint callback 成功后的保存信息
4. `on_train_end()` 的训练完成摘要

#### 类别 2：写日志但不打终端
以下全部改为 logger.debug 或 logger.info(file only)：
- `[Rank 0] Starting Ray initialization...`
- `[Rank 0] Calling ray.init ...`
- `[DEBUG] Generated ...`
- `[DEBUG] After filter ...`
- `[DEBUG] Rewards min/max/mean`
- QED/SA 列表长度和 min/max
- batch 级中间信息

#### 类别 3：真正异常才上终端
只保留：
- reward 计算失败
- advantages 缺失
- checkpoint 目录丢失
- 无法保存 checkpoint
- 训练中断

### epoch 汇总输出建议格式
把当前单行拼接改成更可读的块状排版：

```text
[Epoch 1/5]
  Loss        : -0.0690
  Reward      :  0.0722
  Avg QED     :  0.0000
  Avg SA      :  0.0000
  Valid Ratio :  1.0000
```

这比现在的：
- `Loss: ..., REWARD: ..., AVG_QED: ...`

更适合终端快速扫读。

### 预期效果
终端每个 epoch 只出现：
- 进度行
- 生成完成
- 一个简洁汇总块
- 一条 checkpoint 信息

而不是夹杂十几条 `[DEBUG]`。

## 5.5 采样进度层：保留单行覆盖，但避免被其他 warning 打断

文件：`ddpo/integration/diffsbdd_model.py`

### 当前优点
这里已经有你想要的核心形式：
- `[Epoch ?] 生成中: ...` 单行覆盖
- `[Epoch ?] 生成完成: ...`

### 当前问题
它会被以下内容打断：
- RDKit / OpenBabel stderr
- `print('Warning: CoG drift ...')`
- 其他直接 `print()`

### 建议改法
1. **保留当前单行覆盖机制**
2. 把内部 warning 改成写日志，不打终端
3. 若必须提示终端，改成 epoch 结束后聚合摘要，而不是在生成过程中插队打印

例如：
- 不要在扩散 loop 里打印 `Warning: CoG drift`
- 改为记录计数，在 epoch end 输出：
  - `Sampling warnings this epoch: CoG drift occurred in 2 batches (details in log)`

### 预期效果
单行进度条就能保持稳定，不会被穿插打断。

---

## 5.6 checkpoint 输出：必须基于真实 callback 结果，而不是目录扫描

文件：`ddpo/trainer/lightning_ddpo_module.py`

### 当前问题
现在 checkpoint 信息来自“扫目录看见 `.ckpt` 就打印 saved”。
这会导致误报。

### 建议改法
后续真正实现时，checkpoint 输出必须基于：
- `ModelCheckpoint` 回调对象的真实路径
- 或 `on_save_checkpoint()` 已实际触发后的路径

不要再用：
- `os.listdir(checkpoint_dir)`
- `sorted(...)[-1]`

来充当“保存成功证明”。

### 理想输出
```text
[CHECKPOINT] Epoch 1: Saved /.../checkpoints/last.ckpt (11.6MB)
```

或者短版：
```text
[CHECKPOINT] Epoch 1: Saved last.ckpt (11.6MB)
```

但前提是该路径必须来自真实 callback，而不是目录猜测。

### 预期效果
checkpoint 信息将从“可能误导”变成“可以信赖”。

## 9. 最后一句总结

这次问题的本质不是“日志太多”这么简单，而是：

> **当前系统没有把“终端可读性”和“详细可追溯日志”分层。**

正确的方向不是简单粗暴地静默一切，而是：

- **终端只保留训练决策层信息**
- **详细技术噪声全部进入日志文件**
- **checkpoint 信息必须基于真实保存事件**

这样既能让训练现场清爽，又不会牺牲科学代码排查所需的可追踪性。
