## 2. 最终结论（先给结论）

### 结论 A：`batch0` 的**根本来源**是 Lightning 的 `batch_idx=0`

你当前这条训练链路里，**每个 epoch 只会产生 1 个 batch**。
因此这个 epoch 内唯一的 batch，自然就是：

- 第 0 个 batch
- 即 `batch_idx = 0`
- 人眼看到就是 `batch0` 或 `Batch 0`

所以：

> `batch0` 并不一定代表“多出来了一个奇怪 batch”，它首先是当前 dataloader 设计下的**唯一 batch 的标准编号**。

---

### 结论 B：但代码里**确实存在一个真实 bug / 设计缺陷**：记录器把 batch 编号**写死成 0**

在 `ddpo/trainer/lightning_ddpo_module.py` 的 `forward()` 中，记录器调用不是用真实 `batch_idx`，而是直接写死：

- `self.molecule_recorder.record_batch(self.current_epoch, 0, samples)`

这意味着：

1. 即使未来一个 epoch 里有多个 batch，记录文件里的 batch 字段也仍然会写成 `0`
2. 会造成日志和 CSV 的 batch 语义被污染
3. 用户看到 `batch0` 时，很容易误以为是底层别的模块、旧代码、或者某种“残留 batch 名称”造成的

所以：

> `batch0` 一半是“当前单-batch/epoch 设计下的正常现象”，另一半则是“记录器硬编码 0 导致的可疑混淆点”。

---

### 结论 C：当前训练链路还存在**输出路径混用 / 记录归档漂移**问题

本次运行的训练日志正确落在：

- `OUT/diffsbdd-ddpo-qed-sa-test_20260323_193553/training_20260323_193553.log`

但 `MoleculeRecorder` 生成的文件却出现在仓库根部：

- `molecules/molecules.csv`
- `molecules/epoch_statistics.csv`

而不是稳定地落到本次运行目录 `OUT/diffsbdd-ddpo-qed-sa-test_20260323_193553/molecules/`。

这说明：

- 当前 Lightning 训练器的 `default_root_dir`
- 自己创建的 `output_dir`
- `TensorBoardLogger.save_dir`
- `MoleculeRecorder(output_dir)`

这几条路径链路**没有严格对齐**。

所以本问题不是只有 `batch0` 一个点，实际上还伴随：

1. batch 编号记录不严谨
2. 输出目录不统一
3. 终端输出、训练日志、CSV 文件的来源感知不一致

## 3. 调查链路还原

## 3.1 实际启动脚本不是旧入口，而是 Lightning 主入口

用户说明训练使用：

- `scripts/run_rl_qed_sa_test.sh`

该脚本实际执行的是：

- `ddpo/main_diffsbdd_lightning.py`

即不是旧的 `ddpo/main_diffsbdd.py` 直接训练，而是 **Lightning 主线入口**。

这点很关键，因为如果误以为走的是旧入口，就会把很多 `batch0` 归因到 legacy 脚本或旧 trainer。

实际不是。

---

## 3.2 配置里 `epochs=5`，但这不等于“每个 epoch 5 个 batch”

配置文件：`configs/ddp_gpu_qed_sa_test.yaml`

其中：

- `dataloader.epochs: 5`
- `train.batch_size: 16`
- `ddp.num_gpus: 2`
- `sample_group_size: 1`
- `each_prompt_sample: 8`

日志里也打印：

- `Batch size: 8`
- `Num batches: 5`
- `Max epochs: 5`

这里**很容易误导**：

- `Num batches: 5` 这个打印，看起来像“每个 epoch 有 5 个 batch”
- 但实际 DataLoader 的 `__len__()` 明确返回的是 `1`
- `Trainer(max_epochs=5)` 才是训练总轮数来源

也就是说真实语义是：

- 每个 epoch：1 个 batch
- 共训练 5 个 epoch
- 所以总共执行 5 次 training step
- 每次 training step 的 `batch_idx` 都会从 0 开始

因此每个 epoch 里看到 `Batch 0` 是完全自然的。

---

## 4. `batch0` 的源码来源定位

## 4.1 真正的 batch 编号来自 Lightning 的 `training_step(batch, batch_idx)`

`ddpo/trainer/lightning_ddpo_module.py` 中定义了：

- `def training_step(self, batch, batch_idx):`

这说明 batch 编号来自 PyTorch Lightning 的标准回调参数。

后面还有打印：

- `f"[Epoch {current_epoch}/{max_epochs}] Batch {batch_idx}: ..."`

因此，如果控制台或日志里出现 `Batch 0`，**第一来源**就是 Lightning 正常传入的 `batch_idx=0`。

---

## 4.2 为什么总是 0：因为这个 DataLoader 每个 epoch 只产 1 个 batch

`ddpo/main_diffsbdd.py` 中 `DiffSBDDDataLoader` 的关键逻辑是：

- `__len__()` 返回 `1`
- `__next__()` 中若 `current_batch >= 1` 就 `StopIteration`

这意味着：

- 一个 epoch 内只会拿到 1 次 batch
- 这唯一一次 batch 的编号就是 0

所以从 Lightning 视角：

- epoch 1 有 `Batch 0`
- epoch 2 还是 `Batch 0`
- epoch 3 还是 `Batch 0`

这不是多出来的 batch，而是**每个 epoch 的首个且唯一 batch**。

---

## 4.3 记录器中的 `batch=0` 是硬编码，不是真实传参

更关键的问题在这里。

在 `ddpo/trainer/lightning_ddpo_module.py` 的 `forward()` 中，记录分子时调用：

- `self.molecule_recorder.record_batch(self.current_epoch, 0, samples)`

注意这里第二个参数不是 `batch_idx`，而是字面值 `0`。

这表示：

- 分子记录 CSV 中的 `batch` 列，不依赖 Lightning 真实 batch 编号
- 而是**永远写 0**

这个实现有两个后果：

### 后果 1：当前单-batch 设计下，不容易暴露问题

因为当前每个 epoch 本来就只有 1 个 batch，所以真实 `batch_idx` 本来也确实是 0。
因此这个 bug 会被“正常现象”掩盖掉。

### 后果 2：一旦以后改成多 batch，这里一定出错

如果后续你把 dataloader 改成：

- 每个 epoch 多个 batch
- 或者真正基于数据集迭代

那么：

- Lightning 真实 batch 可能是 0,1,2,3...
- 但 CSV 记录全都会写成 0

这会直接导致：

- 分析脚本误判
- 用户以为 batch 混乱
- 排查训练行为时看不到真实批次边界

因此这不是“只是命名不好看”，而是**一个真实的数据记录 bug**。

## 5. 为什么你会怀疑存在“混用”——你的直觉是对的

你怀疑可能有 bug 或混用，这个判断是对的，但要分层看。

## 5.1 不是旧脚本和新脚本混用了训练主入口

本次使用的是：

- `scripts/run_rl_qed_sa_test.sh`
- 实际进入 `ddpo/main_diffsbdd_lightning.py`

所以不是：

- 某个历史脚本偷偷接管了训练

至少在**主入口层面**，没有发现“走错入口”的混用。

---

## 5.2 但存在“配置语义”和“打印语义”的混用/误导

`main_diffsbdd_lightning.py` 会打印：

- `Num batches: 5`

这个值来自：

- `num_batches=config["dataloader"].get("epochs", 100)`

然而 DataLoader 的真实迭代长度又被 `__len__()` 写死成 `1`。

因此这里存在语义错位：

- `self.num_batches = 5`
- 但 `len(dataloader) = 1`

这会给人一种错觉：

> 看起来应该有 5 个 batch，为什么日志里老是 batch0？

其实真实情况是：

- 这 5 代表 epoch 总数，不代表每个 epoch 的 batch 数

所以这是一个**打印/命名层面的误导问题**。

---

## 5.3 还存在“训练输出目录”和“分子记录目录”混用

本次运行目录为：

- `OUT/diffsbdd-ddpo-qed-sa-test_20260323_193553/`

训练日志也确实在该目录下：

- `training_20260323_193553.log`

但分子记录文件并没有出现在这个目录，而是出现在仓库根目录：

- `molecules/molecules.csv`
- `molecules/epoch_statistics.csv`

这非常可疑，说明以下几者至少有一个没有对齐：

1. `output_dir`
2. `trainer.default_root_dir`
3. `TensorBoardLogger(save_dir=output_dir, name="lightning_logs")`
4. `MoleculeRecorder(output_dir)` 里拿到的 output_dir

当前代码里 `MoleculeRecorder` 是这样初始化的：

- `output_dir = self.trainer.default_root_dir or "./outputs"`
- `self.molecule_recorder = MoleculeRecorder(output_dir)`

而 checkpoint 查询也依赖：

- `self.trainer.default_root_dir or "./outputs"`

问题是：`pl.Trainer(...)` 创建时并没有显式传入 `default_root_dir=output_dir`。
这就使得 Lightning 内部默认根目录，未必与你自己上层算出来的 `output_dir` 一致。

这会造成：

- 训练 log 在 `OUT/...`
- TensorBoard 在 `OUT/.../lightning_logs/...`
- 分子 CSV 跑到 `./molecules`
- checkpoint 目录查询也可能偏移

因此，**你怀疑有混用，确实成立**，只是混用点主要在“输出路径体系”和“记录器语义”，不在训练入口本身。

## 8. 最可能的“认知错位”来源

你之所以会对 `batch0` 产生强烈疑问，我判断是以下几个因素叠加：

### 因素 1：配置里有 `epochs: 5`
用户自然容易理解成“会有 5 个 batch”。

### 因素 2：日志里打印了 `Num batches: 5`
进一步强化“应该有 batch1/batch2/batch3”的预期。

### 因素 3：实际 DataLoader 每个 epoch 只有 1 个 batch
这和直觉不一致。

### 因素 4：记录器又硬编码成 `0`
导致你无论看哪里，几乎都只能看到 `batch0`。

### 因素 5：输出路径还不统一
进一步让人怀疑是不是多个模块在同时写不同地方。

所以你对 `batch0` 的怀疑并不是多虑，而是当前工程实现确实容易造成这种错觉。

## 9. 建议修复方案（按优先级排序）

## P0：修复记录器 batch 硬编码

当前：

- `self.molecule_recorder.record_batch(self.current_epoch, 0, samples)`

应改为：

- 将 `batch_idx` 传入 `forward()` 或直接在 `training_step()` 中调用记录器
- 使用真实 `batch_idx`

例如思路：

1. `forward(self, batch, batch_idx)`
2. `training_step()` 调 `self.forward(batch, batch_idx)`
3. `record_batch(self.current_epoch, batch_idx, samples)`

这是最关键修复。

---

## P1：统一 DataLoader 的“num_batches”语义

当前：

- `self.num_batches` 来自配置的 `epochs`
- 但 `__len__() == 1`

建议二选一：

### 方案 A：保留“每 epoch 仅 1 batch”设计
那就应该：

- 删掉或重命名 `num_batches`
- 打印成 `Total planned epochs` 而不是 `Num batches`

### 方案 B：真的让 dataloader 每个 epoch 产生多个 batch
那就应让：

- `__len__()` 返回真实批次数
- `__next__()` 跟随 `self.num_batches`

就当前代码看，**方案 A 更符合现状**，也更简单。

---

## P1：统一输出目录

建议在创建 `pl.Trainer` 时显式设置：

- `default_root_dir=output_dir`

这样至少：

- `MoleculeRecorder`
- checkpoint
- 训练默认根目录

会和本次运行目录对齐。

否则当前就会出现：

- 一部分输出在 `OUT/<run>/`
- 一部分输出在仓库根部 `molecules/`

这非常不利于实验管理。

---

## P2：修正调试打印的语义一致性

例如：

- `Generated 0 molecules`
- `After filter: 8 molecules`

建议明确区分：

- 生成的轨迹数
- 成功解码出 SMILES 的数量
- 过滤前样本数
- 过滤后保留样本数

否则调试信息会误导调查。
