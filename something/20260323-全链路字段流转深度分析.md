## 2. 一图总览：字段流转主路径

```text
DataLoader.generate_batch()
  -> batch: {nodesxsample, group_index}

Rollout.generate_minibatch()
  -> batch: {
       x, categorical,
       latents, logps, timesteps,
       nodesxsample, group_index
     }

Filter.filter()
  -> 计算 smiles（用于过滤与日志）
  -> 可选去重/筛选
  -> 返回 filtered_data, filtering_ratio, novelty_penalty_ratio

Reward.calculate_rewards()
  DruglikenessReward:
    写入 rewards, qed_scores, sa_scores
  CompositeReward:
    最终写回 rewards，附带 druglikeness_reward

Lightning.forward()
  -> 若无 advantages: advantages = rewards
  -> actor.update_policy(samples)
  -> metrics 来自 actor（含 Loss, ClipFrac）+ batch_stats + reward

Lightning.training_step()
  -> 打印: Loss / Reward / QED / SA / Valid

MoleculeRecorder
  -> record_batch(), compute_batch_stats(), record_epoch_statistics()
  -> 输出 molecules.csv, epoch_statistics.csv
```

## 3. 分阶段字段语义梳理

## 3.1 DataLoader 阶段（prompt 构造）

`DiffSBDDDataLoader.generate_batch()` 输出字段：

- `nodesxsample`
- `group_index`

`meta_info`：

- `max_n_nodes`
- `condition=False`

额外语义：

- `__len__()` 固定返回 `1`
- 每个 epoch 只产 1 个 batch（这解释了每个 epoch 的 `Batch 0`）

---

## 3.2 Rollout 阶段（生成轨迹）

`DiffSBDDRollout.generate_minibatch()` 在输入 prompt 基础上生成：

- `x`：原子坐标
- `categorical`：原子类别 one-hot
- `latents`：扩散轨迹（堆叠后）
- `logps`：旧策略轨迹对应 log prob
- `timesteps`：时间步
- `nodesxsample`
- `group_index`

这一阶段还做了轨迹对齐注释（给 actor 用）：

- `latents[:, :T+1]` 对齐当前
- `latents[:, 1:]` 对齐 next_latents
- `logps` 与 `timesteps` 对齐

结论：

- rollout 阶段字段比较清晰
- 训练核心轨迹字段（latents/logps/timesteps）是完整的

---

## 3.3 Filter 阶段（合法性与可选去重）

`DiffSBDDFilter.filter()` 主要做：

1. 从 `x/categorical/nodesxsample` 重建分子
2. 计算 `smiles`
3. 可选去重（`enable_filtering`）
4. 可选新颖性惩罚（`enable_penalty`）
5. 返回 `filtered_data, filtering_ratio, novelty_penalty_ratio`

关键现象（高重要）：

- 日志常见 `Generated 0 molecules` 但 `After filter: N molecules`
- 这通常反映“不同阶段看的字段不同”：
  - 生成后立刻看 `smiles` 可能还没写入
  - filter 后写入了 `smiles`，长度变为 N

因此这组日志不一定代表生成失败，而是字段生成时机不同。

---

## 3.4 Reward 阶段（QED+SA）

### 3.4.1 `DruglikenessReward` 实际写入字段

`ddpo/rewards/druglikeness.py` 中明确写入：

- `data.batch['rewards']`
- `data.batch['qed_scores']`
- `data.batch['sa_scores']`

其中：

- `rewards` 默认先置 `-1.0`（失败惩罚）
- 成功分子则替换为 `0.5 * QED + 0.5 * normalized_SA`
- `sa_scores` 存的是 **原始 SA（1~10）**

### 3.4.2 `CompositeReward` 行为

当前配置仅 `druglikeness:1.0`，因此 composite 最终：

- 仍写回 `data.batch['rewards']`
- 额外写 `data.batch['druglikeness_reward']`

结论：

- reward 主链路是通的
- `Reward` 非零与此一致

---

## 3.5 Actor 阶段（PPO更新）

`EDMActor.update_policy()` 使用字段：

- `advantages`
- `latents`
- `next_latents`
- `timesteps`
- `logps`
- `nodesxsample`

损失核心：

- `ratio = exp(log_prob_current - log_prob_old)`
- PPO clipped objective
- 最终返回 metrics：
  - `Loss`
  - `ClipFrac`

Lightning 中若缺失 `advantages`，会设置：

- `advantages = rewards`

所以：

- `Loss` 与 `Reward` 数值相关是正常的
- `Loss` 不是 QED/SA 的监督损失

---

## 3.6 Lightning 日志阶段（关键错配点）

`lightning_ddpo_module.py` 在 reward 之后读取：

- `qed_list = samples.batch.get('qed', [])`
- `sa_list = samples.batch.get('sa_raw', [])`

但 reward 实际写的是：

- `qed_scores`
- `sa_scores`

这构成**明确字段错配**。

直接后果：

- `QED list length: 0, SA list length: 0`
- `avg_qed` / `avg_sa` 走默认 0
- 训练打印 `QED=0.0000, SA=0.0000`

同时 reward 打印来自 `rewards`，该字段是通的，所以会出现：

- `Reward` 非零
- `QED/SA` 却为 0

这不是科学结果本身矛盾，而是统计字段读取不一致。

---

## 3.7 Recorder 阶段（第二个错配放大器）

`MoleculeRecorder` 也读取：

- `qed`
- `sa_raw`

而不是 `qed_scores` / `sa_scores`。

结果：

- `compute_batch_stats()` 经常把 `avg_qed/avg_sa` 置 0
- `record_batch()` 因 `zip(smiles,qed,sa,reward,valid)` 受空列表影响，明细写入很容易退化
- `epoch_statistics.csv` 常出现全 0 统计

这解释了你看到的：

- 日志里 QED/SA 为 0
- CSV 里 QED/SA 也为 0

二者是同一错配链路导致的，不是两处独立问题。

---

## 4. 已确认问题清单（按严重度）

## P0（高严重）：奖励输出字段与日志/记录输入字段不一致

- 写：`qed_scores`, `sa_scores`
- 读：`qed`, `sa_raw`

影响：

- QED/SA 显示与统计失真
- 用户误判训练是否真正计算性质

---

## P0（高严重）：`Loss` 与性质指标并排显示但缺少语义边界

- `Loss` 是 PPO policy loss
- `QED/SA` 是分子性质统计

当前展示容易让人误以为是统一监督学习看板。

影响：

- 读数解释被混淆
- 排障效率降低

---

## P1（中严重）：记录器字段读取与 reward 协议脱节

`MoleculeRecorder` 的输入字段约定没有随 reward 输出更新。

影响：

- CSV 统计不可直接用于真实科学判断
- 下游分析脚本可能被误导

---

## P1（中严重）：单 epoch 单 batch 语义与打印文案认知差

- 实际：`__len__()==1`
- 用户看到常常会期待“多个 batch 的连续编号”

影响：

- `Batch 0` 被误判为异常

---

## 5. 你关心的现象如何统一解释

现象：

- `Loss=0.7838, Reward=-0.7848, QED=0.0000, SA=0.0000`

统一解释：

1. `Loss`：来自 PPO 更新，正常
2. `Reward`：来自 `rewards` 字段（通路正常）
3. `QED/SA`：来自错配字段读取（统计层掉到默认 0）

因此“Reward 非零而 QED/SA 为 0”不表示科学逻辑自相矛盾，而是日志字段协议断裂。

---

## 6. 证据置信度分层

### 高置信（源码直接确认）

- `DruglikenessReward` 写 `qed_scores` / `sa_scores`
- Lightning 读 `qed` / `sa_raw`
- `MoleculeRecorder` 也读 `qed` / `sa_raw`
- `Loss` 来自 `EDMActor.update_policy()` 的 PPO metrics
- `advantages` 缺省等于 `rewards`

### 中置信（运行现象与源码一致推断）

- 日志中 `QED list length: 0` 来自字段错配
- CSV 全 0 统计主要由同一错配链路放大

---

## 7. 对实验可解释性的影响

如果不修复字段协议，当前训练过程存在如下风险：

1. **误判模型训练状态**：误以为 QED/SA 没计算
2. **误判奖励机制**：误以为 reward 不依赖性质
3. **误判收敛质量**：看板中 QED/SA 曲线不可信
4. **误导实验结论**：CSV 统计不能直接用于科学汇报

---

## 8. 结论总结（简短版）

- 当前链路的“训练语义”是通的（rollout/reward/actor）
- 当前链路的“性质统计语义”是断的（logger/recorder 字段错配）
- `Loss` 输出正常，`QED/SA=0` 主要是显示/统计协议问题
- 该问题不是局部打印 bug，而是跨模块字段契约不一致

---

## 9. 后续建议（本报告不改代码，仅给方向）

建议你后续做一个“字段契约统一表”，并在每个边界处显式校验：

- rollout 输出契约
- filter 输出契约
- reward 输出契约
- logger 输入契约
- recorder 输入契约

尤其要把以下字段统一到一套命名：

- QED: `qed` vs `qed_scores`
- SA: `sa_raw` vs `sa_scores`
- valid: 是否由 filter/reward/recorder统一维护

这一步做完后，你的日志、CSV、和 reward 行为才会重新对齐。
