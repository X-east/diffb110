## 2. 最终结论（先说结论）

### 结论 A：`Loss` 的出现是正常的，它不是 QED/SA 的损失，而是 **PPO 策略更新损失**

你当前这条训练链路虽然奖励函数只使用 `DruglikenessReward(QED+SA)`，但整体仍然是 **DDPO / PPO 强化学习训练**。

因此：

- `Reward` 是奖励信号
- `Loss` 是 actor 根据 reward/advantage 反向更新扩散策略时计算出的 **策略优化目标**

也就是说：

> 这条日志里的 `Loss=0.7838` 不是“分子性质回归误差”，也不是 “QED/SA 的监督损失”，而是 PPO 风格 policy loss 的均值。

---

### 结论 B：这条日志里的 `QED=0.0000, SA=0.0000`，**大概率不是实际所有分子的 QED/SA 都真的为 0**

更大的可能是：

> 奖励模块写入的字段名，与 Lightning 模块/记录器读取的字段名不一致，导致统计逻辑读不到真实值，最后回退成 0。

已经确认的字段不一致是：

#### 奖励模块实际写入：
- `qed_scores`
- `sa_scores`

#### 训练模块和记录器实际读取：
- `qed`
- `sa_raw`

这会直接导致：

- `samples.batch.get('qed', [])` 取到空列表
- `samples.batch.get('sa_raw', [])` 取到空列表
- 批次统计函数把空列表平均值默认写成 `0.0`
- 最终打印出：`QED=0.0000, SA=0.0000`

因此：

> 当前日志里的 `QED=0` / `SA=0`，更像是**统计/日志字段错配导致的“显示为 0”**，而不是药性打分真的普遍等于 0。

---

### 结论 C：`Reward` 非零而 `QED/SA=0` 这一组合，本身就是字段错配的强证据

当前 reward 只启用 `DruglikenessReward`，没有 docking。
因此 reward 理论上只由：

- `QED`
- `SA` 归一化后加权得到

换句话说：

> 如果真实 QED 和 SA 全是 0，那么 reward 不应该稳定地出现非零值（除非失败惩罚或别的路径介入）。

但你的日志里：

- `Reward=-0.7848` 是非零
- 同时 `QED=0.0000, SA=0.0000`

这说明这三者不是来自同一个字段体系。

## 3. 先解释：为什么 RL 训练里会有 `Loss`

## 3.1 你当前不是“只打分不训练”，而是“用 QED+SA 作为 reward 来训练策略”

从配置和入口看，你当前走的是：

- `scripts/run_rl_qed_sa_test.sh`
- `ddpo/main_diffsbdd_lightning.py`

这不是单纯“生成分子然后算性质”的脚本，而是：

- Rollout 生成分子
- Reward 计算分数
- Actor 根据 reward 更新模型参数

也就是说，哪怕奖励里没有 docking，**训练仍然是训练**。

因此有 loss 很正常。

---

## 3.2 Lightning 模块明确会把 actor 的 `Loss` 当作训练损失打印出来

在 `ddpo/trainer/lightning_ddpo_module.py` 中：

1. `forward()` 最后调用：
   - `metrics = self.actor.update_policy(samples)`

2. 然后把：
   - `dummy_loss = torch.tensor(metrics.get('Loss', 0.0), ...)`

3. 再在 `training_step()` 中：
   - `self.log('train_loss', loss, ...)`
   - 并打印 `Loss={loss:.4f}`

所以 Lightning 打印的 `Loss`，本质上就是：

- `EDMActor.update_policy()` 返回的 `metrics['Loss']`

不是别的损失。

---

## 3.3 `Loss` 的数学来源：PPO clipped objective

`RLPF-verl_diffusion/verl_diffusion/worker/actor/edm_actor.py` 中：

- `update_policy()` 调 `train_batched_samples()`
- `train_batched_samples()` 反复调用 `calculate_loss()`
- `calculate_loss()` 中核心逻辑是：

1. 用当前模型重新评估旧采样轨迹的 log prob
2. 计算：
   - `dif_logp = log_prob_current - log_prob_old`
   - `ratio = exp(dif_logp)`
3. 再用：
   - `advantages`
   - `clip_range`
   - `ratio`
   计算 PPO 风格损失

其 `loss()` 核心是：

- `unclipped_loss = -advantages * ratio`
- `clipped_loss = -advantages * clamp(ratio, 1-clip, 1+clip)`
- 返回两者较大的均值

所以这个 loss 的含义是：

> 当前策略相对旧策略，在 advantage 引导下，对扩散轨迹做 policy update 时的 PPO clipped loss。

这和监督学习里的 MSE/CE 完全不是一回事。

---

## 3.4 为什么 reward 是负的，loss 却是正的？

这也是正常现象。

因为这里的损失函数形式本来就是：

- `-advantages * ratio`

当前代码里如果 `advantages` 不存在，会直接设置：

- `samples.batch["advantages"] = samples.batch["rewards"]`

也就是：

- **advantage = reward**

所以当 reward 平均偏负时：

- `advantages` 偏负
- `-advantages` 偏正
- loss 变成正值非常自然

因此像：

- `Reward=-0.7848`
- `Loss=0.7838`

这种数值级别相近、符号相反的现象，是当前实现下完全说得通的。

> 这恰恰说明当前 loss 与 reward 强相关，而不是独立的某个“神秘额外损失”。

---

## 4. 为什么日志里 `QED=0.0000, SA=0.0000`

## 4.1 奖励模块真实写入的字段名

`ddpo/rewards/druglikeness.py` 中，`DruglikenessReward.calculate_rewards()` 的逻辑是：

- 初始化：
  - `qed_scores`
  - `sa_scores`
  - `rewards`

- 对每个分子：
  - 计算 `qed`
  - 计算 `sa_raw`
  - 用 `sa_normalized = (10 - sa_raw) / 9`
  - 组合得到 `reward`

- 最后写回 batch：
  - `data.batch['rewards'] = rewards`
  - `data.batch['qed_scores'] = qed_scores`
  - `data.batch['sa_scores'] = sa_scores`

注意这里**没有写**：

- `data.batch['qed']`
- `data.batch['sa_raw']`

这是关键。

---

## 4.2 Lightning 模块读取的却是另一组字段名

`ddpo/trainer/lightning_ddpo_module.py` 中，奖励算完后，代码读取的是：

- `qed_list = samples.batch.get('qed', [])`
- `sa_list = samples.batch.get('sa_raw', [])`

这和奖励模块写入的字段名不一致：

| 位置 | QED字段 | SA字段 |
|---|---|---|
| `DruglikenessReward` 写入 | `qed_scores` | `sa_scores` |
| Lightning 模块读取 | `qed` | `sa_raw` |

结果就是：

- `samples.batch.get('qed', [])` 拿不到数据 → 空列表
- `samples.batch.get('sa_raw', [])` 拿不到数据 → 空列表

然后这段逻辑会打印：

- `QED list length: 0, SA list length: 0`

这与你终端里的实际 debug 输出是吻合的。

这几乎可以直接判定：

> 训练模块并没有读到 DruglikenessReward 写出的真实 QED/SA 张量。

---

## 4.3 记录器也在读错字段名

`ddpo/utils/molecule_recorder.py` 同样使用：

- `samples.batch.get('qed', [])`
- `samples.batch.get('sa_raw', [])`

而不是：

- `qed_scores`
- `sa_scores`

后果是双重的：

### 后果 1：`compute_batch_stats()` 中平均值直接退化为 0

`compute_batch_stats()` 逻辑：

- 如果 `qed_list` 为空 → `avg_qed = 0.0`
- 如果 `sa_list` 为空 → `avg_sa = 0.0`

所以即使真实打分已算出来，只要字段名读错，日志里仍然会显示：

- `QED=0.0000`
- `SA=0.0000`

### 后果 2：CSV 记录也会空掉

`record_batch()` 用 `zip(smiles_list, qed_list, sa_list, rewards_list, valid_list)` 写分子明细。

但当前：

- `qed_list` 为空
- `sa_list` 为空
- `smiles_list` 也可能为空或长度不一致

结果就是：

- 分子记录循环根本不执行，或者几乎不执行
- `molecules.csv` 只剩表头
- `epoch_statistics.csv` 显示 `avg_qed=0.0000`、`avg_sa_raw=0.0000`

这与你当前仓库根目录下看到的：

- `molecules/molecules.csv` 只有表头
- `molecules/epoch_statistics.csv` 里 QED/SA 全 0

完全一致。

---

## 4.4 所以“QED 和 SA 打分均为 0”到底是真是假？

严格地说，当前只能下这个结论：

> **日志里显示为 0，不足以证明真实所有分子的 QED/SA 都是 0。**

更准确说法是：

- 日志/统计链路**没有成功读取** reward 模块输出的真实 QED/SA 字段
- 因而打印结果是“默认值 0”
- 这是一种**显示层/统计层错误**，不等于真实打分值就是 0

## 5. 为什么 reward 却是非零？

这恰恰进一步证明了“QED/SA 打印为 0”不是可信的真实结果。

## 5.1 reward 的来源字段是正确的

`DruglikenessReward` 会把最终 reward 写到：

- `data.batch['rewards']`

而 `CompositeReward` 会：

- 读取当前 `data.batch['rewards']`
- 用权重组合到 `combined_rewards`
- 再写回 `data.batch['rewards']`

当前配置里：

- 只有 `druglikeness: 1.0`
- docking 未启用

所以：

- 最终 `rewards` 就是 druglikeness reward 本身

这个字段是连通的，因此 reward 打印能非零。

---

## 5.2 reward 与 QED/SA 打印不一致，说明它们不是从同一套统计字段来的

当前链路：

- reward 从 `rewards` 字段拿值 → 正常
- QED/SA 从 `qed` / `sa_raw` 拿值 → 拿不到 → 默认 0

因此你看到的这组日志：

- `Reward=-0.7848`
- `QED=0.0000`
- `SA=0.0000`

其实应理解为：

> reward 统计链路是活的，QED/SA 显示链路是断的。

---

## 6. 还有一个容易误解的点：为什么 reward 会是负数？

这是正常的，因为当前 reward 对失败分子使用：

- `FAILURE_PENALTY = -1.0`

在 `DruglikenessReward` 中：

- 先把整批 `rewards` 初始化成 `-1.0`
- 只有当分子成功 build + sanitize + 计算性质后，才会把该位置更新成正常 reward

这意味着：

- 若一批分子中大部分无效
- 则平均 reward 很容易显著小于 0

你的终端日志里也有旁证：

- `Rewards: min=-1.0000, max=0.8826, mean=-0.1095`

这说明：

- 至少有部分分子确实成功算出了正向 druglikeness reward
- 也有不少分子落在失败惩罚 `-1.0`

因此 reward 非零、甚至为负，完全合理。

这也进一步否定了“所有 QED/SA 真实都等于 0”的猜测。

## 7. 为什么 `epoch_statistics.csv` 里也是 0？

当前根目录 `molecules/epoch_statistics.csv` 中可以看到：

- `avg_qed=0.0000`
- `avg_sa_raw=0.0000`
- 甚至 `total_molecules=0`

这不是说模型一颗分子都没经历 reward，而是因为：

1. `MoleculeRecorder.record_batch()` 读的是错字段名
2. `smiles/qed/sa_raw` 这些列表为空或长度不匹配
3. 于是 `epoch_data` 根本没被真实填充
4. `record_epoch_statistics()` 最终只能写出一堆 0

所以 `epoch_statistics.csv` 当前不能被当成真实的 QED/SA 统计来源。

## 8. 这条日志里的三个量，分别来自哪？

为了避免继续混淆，把三者来源明确列出来：

### `Loss`
来源：
- `EDMActor.update_policy()` 返回的 `metrics['Loss']`
- 本质：PPO / policy gradient loss

### `Reward`
来源：
- `samples.batch['rewards']`
- 当前配置下本质：`DruglikenessReward` 的最终 reward
- 其中包含：
  - 有效分子的 `0.5 * QED + 0.5 * normalized_SA`
  - 无效分子的 `-1.0` 惩罚

### `QED` / `SA`
来源：
- **不是** reward 模块真实输出字段
- 而是 Lightning/Recorder 错误读取的：
  - `qed`
  - `sa_raw`
- 因字段缺失而回退为 0

所以这三者不是同一层面上的“同步统计量”。

## 9. 这是不是 bug？

答案是：**是，而且是实质性 bug / 统计口径 bug。**

至少有以下已确认问题：

### 已确认问题 1：QED/SA 字段名不一致

- reward 写：`qed_scores` / `sa_scores`
- 训练和记录读：`qed` / `sa_raw`

这会直接造成：

- 日志误报 QED/SA 为 0
- CSV 误报 QED/SA 为 0
- 用户误判训练是否真正算过性质

这是本次问题的主因。

---

### 已确认问题 2：`Loss` 和 `Reward`/`QED`/`SA` 被并排打印，但语义层级不同

- `Loss` 是 PPO loss
- `Reward` 是 sample-level reward 均值
- `QED/SA` 是另一路 batch 统计

它们并排展示并不一定错，但如果没有说明，极易误导用户认为：

- 这是一个统一的 supervised loss + label 指标面板

实际上不是。

---

### 已确认问题 3：记录器统计依赖字段名错误，导致 epoch 统计失真

- `epoch_statistics.csv` 不能反映真实 QED/SA
- `molecules.csv` 也可能空表头

因此当前输出文件不能用于可靠分析 druglikeness 细节。

## 10. 一句话回答你的问题

### 为什么会有 loss 输出？

因为你运行的是 **RL/DDPO 训练**，不是纯打分脚本；`Loss` 来自 actor 的 **PPO 策略优化损失**，用于根据 reward 更新扩散模型策略。
