# 260601-16 重建对比框架解耦与外部资源探测

## 原因

当前 DiffSBDD 的生成流程把“连续点云生成”和“分子重建/成键”耦合得太紧。这样会导致两个问题：

1. 分子质量差时，很难判断是基础模型生成的原子坐标/原子类型本身差，还是 OpenBabel/规则成键把好点云重建坏了。
2. 后续要接 DiffGui、MolSnapper、DecompOpt 或本地 bond predictor 时，如果继续把成键逻辑写死在生成脚本里，会很快变成一堆不可比较的临时脚本。

所以本轮目标不是直接替换成键算法，而是先把 benchmark 拆成可插拔框架：同一批 DiffSBDD 生成点云，只替换 reconstruction backend，指标和报告完全统一。

## 本轮改动

新增模块：

- `DiffSBDD/analysis/reconstruction_benchmark/methods.py`
  - 定义 `ReconstructionMethod` 协议和 `ReconstructionAttempt`。
  - 当前可运行方法：`openbabel`、`edm`。
  - 探测外部 bond predictor / reconstruction 资源，但暂不强行接入。
- `DiffSBDD/analysis/reconstruction_benchmark/metrics.py`
  - 统一逐分子指标：sanitize、valence problem、键长偏差、碎片、最大连通分量、环、芳香环、三元环、稠环、元素组成、形式电荷、QED、SA、LogP、TPSA、HBA/HBD、可旋转键、分子量、Lipinski。
- `DiffSBDD/analysis/reconstruction_benchmark/reporting.py`
  - 统一输出 per-molecule CSV、summary CSV、外部资源 CSV、SDF、PNG 图和 Markdown 报告。
- `DiffSBDD/analysis/reconstruction_benchmark/__init__.py`
  - 暴露 benchmark 主入口，后续 adapter 只需要增加方法类和注册。

重构脚本：

- `DiffSBDD/analysis/generated_reconstruction_ablation.py`
  - 现在只负责加载模型、采样 DiffSBDD atom cloud、调用 reconstruction benchmark。
  - 旧的成键、指标、CSV、画图、SDF 写入逻辑已经迁出。
  - 新增 `--skip-external-probe`，用于跳过外部资源探测。

## 深度判断

### OpenBabel 路线

OpenBabel 的优点是快、成熟、能把点云连成一个相对完整的分子，适合继续作为 baseline 和兜底后处理。

它的主要缺点是对 DiffSBDD 这种连续点云很被动：只要原子距离/类型稍微偏，OpenBabel 会倾向于硬成键，导致键长偏离、芳香性失败、valence/sanitize 错误和奇怪小环。RL 阶段如果只看 docking/classifier，很容易利用这种后处理漏洞。

结论：OpenBabel 不应该再作为唯一成键路径，但应保留为 baseline。

### EDM/距离规则路线

EDM 距离规则更保守，bad bond length 低，速度也快。但它缺少学习到的局部化学上下文，容易漏键，导致碎片化和低 sanitize。

结论：距离规则适合作为下界和 sanity check，不适合作为主线替换。

### DiffGui/MolSnapper bond predictor 路线

这是当前最值得做的中间路线。它不要求立刻改 DiffSBDD 主干扩散变量，只是在同一批 atom cloud 上预测 halfedge/bond type，再进入统一 reconstruction/evaluation。

它能直接回答：

- 如果只替换成键模块，DiffSBDD 的 validity、键长、碎片、三元环和药化指标能不能明显改善？
- 如果改善明显，说明短期论文里可以把“bond-aware reconstruction module”作为模型内部改造一章的一部分。
- 如果改善有限，说明问题主要在 DiffSBDD 点云本身，需要 atom prior、x0 geometry loss 或更深的 edge diffusion。

结论：先接 pretrained / external bond predictor adapter，再决定是否训练本地 predictor。

### 完整 edge diffusion 路线

完整 `x,h,e` diffusion 最彻底，但会改数据格式、transition、denoiser 输入、sampler、decoder、RL logprob 和训练损失，风险比 predictor adapter 大很多。

它适合作为长期完整路线，不适合作为当前第一步。当前应该先用解耦 benchmark 证明“bond 作为独立模块值得改”，再升级到 t-conditioned bond head 或 edge diffusion。

## 下一步建议

优先级 1：接入 DiffGui bond predictor adapter。

- 读取 DiffGui `train_bond.yml`、`bond_predictor.py`、checkpoint state dict。
- 明确输入需要哪些字段：atom type、坐标、halfedge index、pocket/ligand mask、edge candidate。
- 写 `DiffGuiBondPredictorMethod`，输出 RDKit mol 或 bond type 矩阵，指标仍走当前 benchmark。
- 用同一批 n=200 到 n=500 DiffSBDD atom cloud 对比 OpenBabel、EDM、DiffGui predictor。

优先级 2：接入 MolSnapper bond predictor adapter。

- 先从源码恢复模型配置，因为当前探测没有发现独立 config。
- 如果 checkpoint 可加载，加入同一 benchmark。
- 如果 checkpoint 输入强依赖 MolSnapper 自己的数据对象，先记录不可直接接入原因，再决定是否移植结构训练本地 predictor。

优先级 3：训练本地 bond predictor。

- 数据来自 CrossDocked oracle halfedge。
- 输入用 DiffSBDD atom cloud 坐标、atom type、candidate halfedge，目标是真实 bond type。
- 指标先看 bond CE、bond F1，再看 reconstruction validity、bad bond length、fragments、三元环。

优先级 4：再考虑模型内部改造。

- 加 atom composition prior / logits bias，防止元素分布漂移。
- 加 x0 geometry loss，约束局部键长/碰撞。
- 加 t-conditioned bond head，让 denoiser 在不同扩散步学习边信息。
- 最后才升级完整 edge diffusion。

## 剩余风险

- 当前可运行 benchmark 仍只有 OpenBabel 和 EDM；DiffGui/MolSnapper 只是发现了 checkpoint/source，还没有 adapter。
- 当前 benchmark 是“同一批 DiffSBDD 点云的 reconstruction 对照”，不是完整模型生成能力对照。
- n=20 smoke 只验证链路，质量判断应以后续 n=500 或 n=1000 为准。
- OpenBabel 的警告没有阻断输出，但后续报告中应继续统计 sanitize/error 类型，避免只看 validity。
